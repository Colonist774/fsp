# FSP

FSP — веб-платформа для спортивного программирования. Проект сделан для хакатона по кейсу цифровой платформы Федерации спортивного программирования.

Основная идея простая: в одном месте собрать профиль спортсмена, соревнования, регистрацию, результаты и рейтинг. Для онлайн-соревнований мы дополнительно сделали полноценную отправку решений с автоматической проверкой кода.

Это не только набор экранов: основные сценарии работают через backend и PostgreSQL, результаты соревнований влияют на рейтинг, а решения онлайн-задач реально запускаются и проверяются в изолированных Docker-контейнерах.

## Что есть в проекте

Для спортсмена:

- регистрация и авторизация;
- профиль с ФИО, городом, учебным заведением, дисциплинами и спортивным разрядом;
- настройки приватности для ФИО и города;
- список соревнований и регистрация на них;
- личная статистика и история участия;
- общий рейтинг спортсменов;
- просмотр результатов соревнований;
- решение задач прямо на платформе.

Для организатора:

- создание и редактирование соревнований;
- просмотр зарегистрированных участников;
- внесение результатов для внешних соревнований;
- создание задач, примеров и скрытых тестов;
- настройка количества баллов за задачу;
- создание и редактирование анонсов;
- управление спортивными разрядами участников;
- выдача прав организатора другим пользователям.

Для соревнований, которые проходят на платформе, места рассчитываются автоматически по принятым решениям. После завершения соревнования результат фиксируется в профиле участника и учитывается в рейтинге.

## Онлайн-проверка решений

Автопроверка не была обязательной частью основного кейса, но мы решили сделать её, чтобы онлайн-соревнование действительно можно было провести внутри платформы.

Поддерживаются:

- Python;
- JavaScript;
- C++;
- Java.

Каждое решение запускается в отдельном Docker-контейнере без доступа к сети. Для контейнера ограничены память, CPU, количество процессов, время выполнения и объём вывода.

C++ и Java компилируются один раз на отправку, после чего готовая программа прогоняется по скрытым тестам.

Если организатор меняет скрытые тесты, сохранённые решения автоматически перепроверяются. Старый verdict не участвует в standings, пока решение не будет проверено на актуальной версии тестов.

Решение, отправленное до окончания соревнования, учитывается даже в том случае, если проверка закончилась уже после дедлайна. Финальные результаты не фиксируются, пока есть такие незавершённые проверки.

## Рейтинг

Рейтинг складывается из двух частей:

```
рейтинг = баллы за результаты соревнований + баллы за спортивный разряд
```

Количество баллов за место зависит от уровня соревнования. В системе используются пять уровней:

1. региональное;
2. чемпионат / кубок региона;
3. межрегиональное;
4. всероссийское;
5. чемпионат / кубок России.

Чем выше уровень соревнования и итоговое место, тем больше баллов получает спортсмен. Баллы начисляются за места с 1-го по 10-е.

Спортивный разряд даёт отдельный фиксированный бонус. Он влияет на рейтинг, но результаты соревнований остаются основной частью системы: рейтинг можно увеличивать дальнейшими выступлениями.

Полная таблица баллов есть в интерфейсе на странице «Как считается рейтинг».

## Локальный запуск

Нужны Docker, Python, Node.js и npm.

### 1. PostgreSQL

Из корня проекта:

```bash
docker compose up -d
```

По умолчанию база доступна как:

```
postgresql+psycopg://fsp:fsp@localhost:5432/fsp_dev
```

### 2. Backend

```bash
cd backend

python -m venv .venv
source .venv/bin/activate

pip install -r requirements.txt
cp .env.example .env
```

В `backend/.env` нужно заменить `JWT_SECRET` на случайную строку длиной не меньше 32 символов.

Например, секрет можно сгенерировать так:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

После этого применить миграции и запустить API:

```bash
alembic upgrade head
uvicorn app.main:app --reload
```

Backend будет доступен на `http://127.0.0.1:8000`.

Swagger: `http://127.0.0.1:8000/docs`.

### 3. Docker-образы для judge

Runner специально использует уже загруженные образы и не скачивает их во время проверки. Перед первой отправкой решений нужно один раз выполнить:

```bash
docker pull python:3.12-alpine
docker pull node:22-alpine
docker pull gcc:14
docker pull eclipse-temurin:21-jdk-alpine
```

Проверить все четыре языка можно командой:

```bash
cd backend
source .venv/bin/activate
python -m app.judge_smoke
```

Для каждого языка ожидается `status=ok` и `stdout='5'`.

### 4. Frontend

В отдельном терминале:

```bash
cd frontend
npm install
npm run dev
```

После этого открыть `http://localhost:5173`.

Сейчас frontend рассчитан на локальный backend по адресу `http://127.0.0.1:8000`.

## Как получить организатора на чистой базе

Новый пользователь по умолчанию создаётся как спортсмен. Для локальной демонстрации сначала зарегистрируйте пользователя через интерфейс, а затем один раз выполните из корня проекта:

```bash
docker compose exec postgres psql -U fsp -d fsp_dev -c "UPDATE users SET role='organizer', organizer_probation_until=NULL WHERE username='YOUR_USERNAME';"
```

Вместо `YOUR_USERNAME` нужно указать имя зарегистрированного пользователя. После обновления страницы аккаунт получит доступ к функциям организатора.

## Основной сценарий

Самый показательный сценарий для проверки проекта:

1. Организатор создаёт соревнование на платформе.
2. Добавляет задачи, примеры, скрытые тесты и баллы.
3. Спортсмен регистрируется на соревнование.
4. После старта открывает задачи и отправляет решения.
5. Judge проверяет код и формирует текущие баллы и места.
6. После окончания соревнования результаты фиксируются.
7. Результат появляется в профиле спортсмена и меняет его рейтинг.

Для внешних соревнований организатор вместо автопроверки вручную указывает итоговые места участников.

## Несколько деталей реализации

Завершённое соревнование нельзя редактировать, а задачу нельзя удалить после старта. Это сделано специально, чтобы после публикации результатов не менялась история соревнования.

Код отправленных решений хранится 30 дней после окончания соревнования, после чего очищается. Метаданные отправки и итоговый verdict остаются в базе.

Участники с нулевым результатом не получают место. При одинаковом количестве баллов используется спортивное ранжирование: например, результаты `500, 500, 300` дают места `1, 1, 3`.

Организаторы не участвуют в автоматическом standings, даже если используют judge для проверки задач.
